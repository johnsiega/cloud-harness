# One-click draft pull request: design

Status: approved in brainstorming, 2026-11-25. Not yet implemented. Piece 2 of three; it depends on piece 1 ([per-run test command](2026-11-25-per-run-test-command-design.md)), because a pull request needs a run that ends `done`.

## Problem

In v1 the "Push to branch" button only exists for a run that ends `done`, and it always pushes to one fixed private staging repo (`PUSH_TARGET_URL`, today `hospital-queue-harness`). It never targets the repo the agent actually worked on, and it makes only a branch: the human opens any pull request by hand. For the owner's own repos (for example `johnsiega/goats-hsw-rag-chatbot`) the intended flow is "agent finishes, I review the diff, one click, a pull request into main".

## Decisions from brainstorming

- **Target:** the same repo the agent worked on, for repos the owner controls. Forks for other people's repos are **not** in this spec (see "Later").
- **Trigger:** one click, after the user has seen the diff. Never automatic.
- **Not my repo:** if the run's repo is not allowlisted, the button stays today's "Push to branch" to the staging repo. Nothing existing breaks.

## Configuration

- `PR_REPOS=owner/repo,owner/other` in `.env`. Exact match on owner/repo, case-insensitive. This is server config only; a request can never choose its own target.
- `GIT_PR_TOKEN`: a fine-grained GitHub token limited to those repos with Contents: write and Pull requests: write. Separate from the staging-push token (`GIT_PUSH_TOKEN`), which keeps its single-repo scope.
- Without `PR_REPOS` and `GIT_PR_TOKEN`, the feature is off and the UI behaves exactly as in v1.
- `GET /config` reports the allowlist (repo names only, never a token), so the UI can pick the right button.

## Flow

`POST /runs/:id/pr` (guarded like every other route):

1. **Checks.** The run exists, is `done`, has a non-empty diff and a base commit, and its `repoUrl` normalises to an allowlisted `owner/repo`. The feature must be configured (else 503 with how to enable it). One PR per run: a second request answers 409 with the existing PR's number and URL.
2. **Branch.** Reuse the safe mechanics of `api/patch-delivery.ts` (clone the source at the exact base commit, apply the diff with `--binary` to the index, commit as "Cloud harness", push `harness/<runId>`, never force). The target is the source repo itself, with `GIT_PR_TOKEN` passed only through `GIT_CONFIG_*` environment on the calls that talk to the remote. An existing branch answers 409.
3. **Pull request.** Call the GitHub API to create a **draft** pull request from `harness/<runId>` into the repo's default branch (read from the API, not assumed to be `main`).
   - Title: `harness: ` plus the first 60 characters of the task.
   - Body: the task, run id, model, the test outcome (passed, not run with its reason, or failed), and "Generated by Cloud harness. Review before merging." Everything passes through the redactor.
4. **Result.** Store `{ number, url, branch }` on the run and return it. The UI turns the button into a link.

## Safety rules

- Draft only. Never merge, never mark ready for review, never auto-open.
- The token never enters the sandbox; it exists only in the control plane.
- Error mapping: GitHub 403 means "the token lacks permission for this repo"; 404 means "repo or token scope is wrong"; 422 means "a pull request already exists or there is nothing to compare"; a network error means "could not reach GitHub". Messages never contain the token.
- If the default branch moved since the run, GitHub shows any conflict on the PR; the agent is not re-run.
- A repo outside the allowlist can never reach the PR code path.

## UI

`web/src/push-state.ts` gains a "PR" variant. The Diff panel shows **Open draft PR into owner/repo** for allowlisted runs, otherwise the existing **Push to branch**. After success it shows the PR number as a link. Failures reuse the existing inline error style.

## Testing (written first, with a "tests approved" gate)

With fakes for git execution and the GitHub API (no network):
- allowlist matching (exact, case-insensitive, URL forms, a similar-looking repo name rejected);
- the feature-off case (503) and a guarded request;
- the PR title, body and redaction (a secret in the task never reaches GitHub);
- each error mapping (403, 404, 422, network) and that no message contains a token;
- one PR per run, branch exists, and draft is always true;
- the `/config` shape and the UI button choice and states.

Real verification (separate explicit go, a few cents): after piece 1 ships, one real run on `johnsiega/goats-hsw-rag-chatbot`, then press **Open draft PR**. It creates a real draft PR that the owner can close.

## Out of scope

Auto-merge, opening PRs automatically, labels and reviewers, forks, cloning private repos, multiple PRs per run.

## Later (next brainstorms)

- **Private-repo cloning:** needs a read token inside a sandbox that has open internet. A real security trade-off, to be decided on its own.
